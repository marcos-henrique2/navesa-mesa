1. O que é o projeto

navesa-mesa é um sistema interno do Grupo Navesa para automatizar a mesa de precificação de seminovos. Substitui a planilha Excel que era usada pelos gerentes pra precificar carros, analisar margem e produzir relatórios pra contador/sócios/diretoria.

O problema de negócio: a precificação manual em Excel sofria de 4 problemas crônicos: (1) cada loja fazia a sua planilha, sem padrão; (2) margens REAIS só apareciam no fechamento do mês, tarde demais; (3) impossível bater olho e descobrir "carro venenoso" ou "subprecificado"; (4) sem audit trail de quem decidiu o quê. O sistema resolve os 4 com fonte única do NBS DMS + análises automáticas + UI densa pra uso diário.

Fluxo de ponta a ponta

  1. Login — autenticação Supabase Auth com email+senha (sem signup público; contas criadas pelo admin).
  2. Upload de relatórios — o operador sobe 4 arquivos do NBS DMS na tela /upload:
    • Estoque XLSX (veículos atuais no pátio)
    • Vendas XLSX (vendas fechadas — histórico acumulado)
    • Custos detalhados XLS (custos por placa pós-venda)
    • Custos de Estoque PDF (breakdown completo dos carros em estoque)
  3. Processamento automático — parsers validam, normalizam, deduplicam, fazem merge por chassi/placa e persistem no Supabase. Sistema detecta "race de sessão" e faz retry automático se RLS bloquear na primeira tentativa.
  4. Visualização densa — 11 páginas operacionais: Dashboard com KPIs e comparativo mensal automático, Estoque com 19 filtros + tabela TanStack + bulk actions, Análise de Vendas com rankings, Insights com cards clicáveis pra drill-down, Detalhe de cada carro com composição financeira, Chat IA, Histórico de snapshots.
  5. Exportadores corporativos — 3 relatórios XLSX (fórmulas + cores + totalizadores) e 3 versões PDF: Análise Navesa (38 colunas + KPIs), Conferência de Estoque Físico (paisagem A4 pra impressão + assinatura) e Relatório Gerencial (visão executiva).
  6. Observabilidade — dashboard de alertas operacionais clicáveis com drill-down, heatmap por loja, comparativo mês a mês automático, integração FIPE em batch pra calcular subprecificação.

Princípio de segurança central

O sistema exige autenticação em todas as rotas via middleware (proxy.ts) — sem cookies de sessão, qualquer request vai pra /login. As 15 tabelas no Supabase têm RLS authenticated_all_access (auth.uid obrigatório). Em junho/2026 foi adicionada camada extra: CSP completo + HSTS + X-Frame-Options DENY + Permissions-Policy zerada (câmera, microfone, geolocalização). Audit do Cyber Chief (advisory-board) deu score 8,5/10.

4. Arquitetura e stack técnica

Stack pinada

Next.js 16 · React 19 · TypeScript 5 · Tailwind 4 · Supabase (Postgres 17) · @supabase/ssr · Zustand · TanStack Table · AI SDK 6 (multi-provider) · ExcelJS · jsPDF + autoTable · pdfjs-dist · xlsx 0.20.3 · react-dropzone · lucide-react · zod · date-fns · @upstash/redis + @upstash/ratelimit · Node.js 22

Decisões arquiteturais

  • AR-1 — Next.js App Router server-rendered + Client Components. SSR rápido, SEO inerte (app interno).
  • AR-2 — Supabase como backend único: Auth + Postgres + RLS. Sem servidor próprio.
  • AR-3 — Multi-provider AI no /api/chat: fallback automático DeepSeek → Groq → Gemini → Anthropic. Auth check antes do rate limit.
  • AR-4 — Camadas: app/ (pages) → components/ → lib/store/ (Zustand) → lib/data/ (Supabase repos) → lib/parsers/ + lib/export/.
  • AR-5 — Estado global via Zustand (refatoração de React Context em 03/jun) — performance superior, sem re-renders cascateados.
  • AR-6 — Filtros persistidos em sessionStorage via hook usePersistedState com useSyncExternalStore.
  • AR-7 — Dark mode com CSS variables sobrescritas via classe .dark; script inline anti-flicker antes do React montar.
  • AR-8 — Rate limit Upstash Redis fail-open (se Upstash cair, libera o chat — graceful degradation).
  • AR-9 — Filtro central LOJAS_IGNORADAS aplicado no store antes de expor dados — todos os componentes downstream automaticamente ignoram lojas blacklistadas.
  • AR-10 — Helper normalizarPlaca() resolve mismatch entre placas com e sem hífen (XLSX × PDF).

5. Integração real com 4 fontes de dados

O sistema integra com 4 fontes externas reais, cada uma com seus desafios:

5.1 NBS DMS (sistema de gestão da concessionária)

Origem dos dados financeiros. Não tem API — apenas exporta relatórios manualmente. O sistema processa 4 formatos:

  • Estoque XLSX (nbs-xlsx.ts) — 1.220+ veículos no pátio atual
  • Vendas XLSX (nbs-vendas-xlsx.ts) — 1.637 vendas históricas (6 meses)
  • Custos detalhados XLS (nbs-custos-xls.ts) — 1.638 placas com breakdown pós-venda (9 categorias)
  • Custos de Estoque PDF (nbs-custos-estoque-pdf.ts) — 328 carros por loja com markup completo. Parser via pdfjs-dist com análise posicional X-empírica. Validação centavo-perfect: R$ 56.454.469,02 total bateu exato com o relatório do NBS.

5.2 Supabase (Postgres + Auth + RLS)

Backend único. 15 tabelas com RLS authenticated_all_access. Cliente browser via @supabase/ssr com cookie automático. Middleware proxy.ts protege todas as rotas exceto /login e /api/auth/*.

5.3 API FIPE (parallelum.com.br)

Tabela FIPE oficial pra cálculo de subprecificação. Cache em 3 camadas: localStorage (TTL 30 dias) + tabela fipe_cache + tabela fipe_batch (cache de match por chassi). Batch runner processa 1.200+ veículos em ~2min com rate limit nativo da API.

5.4 AI Providers (chat de análise)

Fallback automático em 4 níveis: DeepSeek (free 50 req/dia) → Groq Llama 3.1 (free 30k tokens/min) → Gemini 2.5 Flash (free 250k tokens/min) → Anthropic Claude Haiku (pago — só se todos free falharem). Cada provider tem error capture via onError callback do AI SDK.

Gotchas reais enfrentados (lições caras)

  1. Hydration mismatch em SidebarContent: useState lazy lia localStorage no client mas servidor renderizava com default. Resultado: justify-between no SSR vs justify-center no client → React error.
  2. Sessão race no carregamento inicial: Promise.all disparado antes do cookie de sessão estabelecer → RLS bloqueava silenciosamente → array vazio. Fix: auth.getUser() antes do Promise.all + retry detection.
  3. Placa hífen vs sem hífen: XLSX salva "FPJ-6653", PDF salva "FPJ6653" → 16 placas antigas não casavam. Fix: helper normalizarPlaca() aplicado nos 3 pontos de lookup.
  4. xlsx 0.18.5 CVE: prototype pollution + ReDoS conhecidos. Upgrade pra 0.20.3 via CDN do SheetJS (não está no npm registry).
  5. Heatmap agrupava lojas duplicadas: estoque tinha só cod_empresa, vendas tinham empresa_nome → 2 grupos por loja. Fix: chave canônica em cod_empresa, resolve nome via store.
  6. Cores semânticas em dark mode: CLASSE_COR e CAUTELAR_COR só tinham variants light. Fundo branco com texto invisível em dark. Fix: adicionou variants dark:bg-*-900/40 em todas as 5 classes + 3 cautelares.
  7. Force light mode global: ignorava prefers-color-scheme — feedback do design-squad audit. Migrado pra useSyncExternalStore com toggle Sistema/Light/Dark.
  8. Bug "só hoje aparece" em /vendas no Vercel: combinação de race de sessão + filtros persistidos. Resolvido com fix de race em load().
  9. HoldBack vs ADM no parser PDF: header visual do NBS dizia uma coisa, mas valores caíam em ordem diferente. Parser confia no cluster X observado empiricamente, não no header.
